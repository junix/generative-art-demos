Generative Art Demos

十二幅确定性生成艺术作品的
单文件演示集合

基于 p5.js 与 TypeScript 的生成艺术演示项目——每一幅作品都是一份"一次性渲染、输出透明 PNG"的成品构图， 而非持续循环的动画。通过 URL 参数切换场景，由 Playwright 驱动的无头浏览器完成像素级质量校验。

02系统总览架构

项目由「开发/构建层」「渲染层」「测试层」三层构成，从源码到输出 PNG 形成完整闭环。 渲染层是核心，测试层则像一个独立的质检部门，负责从外部验证输出质量。

图 1 · 三层架构总览

构建层（Build Layer）负责把 TypeScript 源码打包为浏览器可执行的 ESM 模块。 Vite 在这里扮演两个角色：开发时是热更新服务器，测试时是被 Node 子进程启动的静态资源提供者。 入口文件 src/main.ts 只有 104 行，却把十二种生成算法全部内联其中——每个场景都是一个独立的函数。

渲染层（Render Layer）在浏览器 Canvas 上实际绘制图像。 场景路由通过 URL 的 scene 参数实现：渲染器字典 {'flow-field': flowField, 'reaction': reaction, ...} 将字符串 ID 映射到对应的绘制函数。所有场景都设置 noLoop()——只渲染一帧，完成后将 window.__VIS_READY__ 置为 true，向外部测试脚本发出"渲染完成"信号。

测试层（Test Layer）是质量把关的关键。Playwright 驱动无头 Chromium 访问每个场景， 截图保存为带 Alpha 通道的 PNG。然后 pngjs 逐像素分析：透明像素比例需 > 8%、可见像素 > 3.5%、 彩色像素 > 2500 个——三重阈值确保画面既不空白、也不满屏涂抹、且有足够的色彩层次。

03场景渲染管线

单个场景从 URL 到像素输出的完整过程。这是一个线性管线：参数解析 → 画布初始化 → 算法绘制 → 完成标记。

图 2 · 单场景渲染流程

每个场景的渲染都遵循完全相同的五步管线。第一步从 URL 查询参数中读取 scene， 默认值为 flow-field——即使参数缺失或拼写错误，也会回退到流场场景而不是白屏。

第二步创建 1400×900 的 Canvas 画布，并设置像素密度为 1（避免高清屏放大导致测试尺寸漂移）。 关键操作是 randomSeed(42) 与 noiseSeed(42)——这两个调用把所有随机性钉死在同一起点， 确保每次刷新输出完全相同的图像。

第三步通过对象字典进行渲染器分发。十二种算法函数各有各的绘制逻辑，但对外接口统一： 接收一个 p5 实例作为参数。这种"字典路由"模式比 switch-case 更易扩展，也便于测试遍历。

第四步是实际绘制，每个渲染器内部又分为三层：调用 heading() 绘制标题与副标题 （保持全系列视觉统一）、执行核心生成算法（差异最大的部分）、添加装饰性点缀（散布的小圆点等"设计调味"）。 最后调用 noLoop() 让 p5 停止动画循环——这是项目的核心设计选择：成品而非过程。

第五步设置全局完成标志 __VIS_READY__ = true，这是测试脚本等待的"就绪信号"。 此外还有一条并行的交互契约路径：鼠标移动和点击事件会递增 __INTERACTION_COUNT__， 测试脚本通过模拟鼠标操作后读取该值，验证交互事件确实被绑定和触发。

06关键设计决策

项目虽小，但在"成品而非过程"、"确定性而非随机"、"像素级测试而非断言"等方向上做了明确的取舍。

成品构图 vs 过程动画。 大多数 p5.js 演示是实时动画，而本项目选择了 noLoop() 模式——每个场景只渲染一帧静态作品。 这样输出的是可直接使用的设计素材（透明 PNG），而不是需要屏幕录制才能分享的动态过程。 测试也因此变得简单：等待"渲染完成"标志，然后截图校验，不需要处理动画帧同步。

确定性种子。 randomSeed(42) 与 noiseSeed(42) 让每一次渲染都输出完全相同的图像。 对于生成艺术演示项目来说，"每次刷新都有惊喜"可能更符合直觉，但确定性带来了可测试性—— 图像可以做像素级回归对比，代码变更不会因为"随机差异"掩盖真实的视觉退化。

离线测试 + 请求拦截。 Playwright 的 page.route() 拦截了所有非本地的网络请求，防止字体加载、远程资源等外部依赖 导致的测试不稳定。这也意味着测试可以在无网络环境下运行，输出只取决于代码本身。

像素阈值而非像素对比。 测试没有用"与参考图完全一致"的像素比对，而是用了三个统计阈值（透明度、可见度、色彩丰富度）。 这是有意的选择：不同 Chrome 版本、不同渲染后端（SwiftShader vs 硬件加速）可能产生亚像素级差异， 严格的像素匹配会产生误报。统计阈值在"画面质量"层面做断言，对实现细节的容忍度更高。

单文件内联 vs 模块化拆分。 所有十二个渲染器都写在同一个 main.ts 里，没有拆分成多个模块。 这是一个权衡：对于演示性质的项目，单文件浏览成本更低，复制粘贴也更方便； 代价是文件行数偏多，但函数间相互独立，认知负担并不高。
